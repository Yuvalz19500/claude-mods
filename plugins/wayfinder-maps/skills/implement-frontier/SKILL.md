You have been given a spec. Its tickets form a **task graph** with blocking relationships, and the tickets ready now are its **frontier**: open, unclaimed, every blocker done, nothing waiting on a human.

Your job is one **wave**: implement every frontier ticket as it stands when you start, on one branch and one draft PR, then stop. Tickets that unblock during the wave belong to the next wave, which the user starts when they have checked this one.

Communicate with subagents sparsely, through **context pointers** to the spec, tickets, research notes and commits, rather than restating them. Run **implementer subagents** in the background for maximum concurrency.

Two rules hold for every subagent this run starts, and every brief says them:

- **Latest versions, no deprecated APIs.** Code against the versions of the libraries, frameworks and tools the repo actually has installed (read the lockfile or manifest), and read their current documentation before using an API. Never use functionality those versions mark deprecated; when existing code you touch uses it, move that code to the current replacement.
- **Lean tests during the wave.** While implementing, merging and fixing, run only change-aware tests: the tests the change affects, picked by the repo's affected-tests command or a change-aware option of whatever the project uses (for example Playwright `--only-changed`, Vitest `--changed`, Jest `--onlyChanged`, pytest-testmon, Nx or Turborepo `affected`, a game engine's runner filtered by area). Combine them where the stack allows: a build system that picks the changed packages or targets, with per-package result caching keyed by a hash of each package's input files so an unchanged package replays its cached result instead of rerunning, then the runner's own changed-only mode inside each package that does run. Never the full suite. The `lean-tests` skill holds the policy and the tools; if the repo has no affected-tests command yet, set one up yourself with it (don't hand the user steps) right after step 4, as the wave branch's first commit, before starting implementers, and until then fall back to the full suite where the affected run would go. The full suite runs once per wave, right before it merges, and every failure it shows gets fixed (see step 7).

## Steps

1. Read the spec and its tickets, enough to understand the task graph. Fix the wave: list the frontier tickets by number and title. Done when the list is written down; it does not change for the rest of the run. With an empty frontier, report what blocks it (blocked tickets, tickets waiting on the user) and stop.

2. Claim the wave: set each wave ticket's status to claimed where the tracker keeps it (the ticket file's `Status:` line, or an assignee on the issue).

3. (optional) Use an **exploration subagent** for exploration the wave's tickets need: relevant codebase files or external documentation. It saves its markdown notes in a directory outside the repo that every later subagent can read, so implementers spend their run implementing.

4. Create a branch and a draft PR for the wave. The PR closes the wave's tickets, and only those.

5. Start one **implementer subagent** per wave ticket, each in its own worktree, on its own branch named `<wave branch>--<ticket number>`, so every implementer branch is findable by the wave's prefix. Brief each one to do what `/implement` does for its single ticket: `/tdd` at pre-agreed seams where possible, every test it writes or changes passed through the `test-audit` skill's authoring gate when that skill is available (each test names the behavior it protects and the bug that would fail it, sits at the cheapest layer that catches that bug, and extends an existing test instead of copying one), the latest-versions rule above, typecheck and single test files regularly, then at the end only the cheap layers its change affects (type checks, lint and quick stages, the unit or backend tests and the pure model specs that start no app), never the full suite, then commit to its branch. **Implementers run no end-to-end tests** (no app build, no browser or app specs): they write and extend the end-to-end specs their ticket needs, confirm with a dry run of the affected-tests command (where it has one) that those specs get picked, and list them in their report. The wave's one affected end-to-end run in step 7 runs them, once, on the merged code. Implementers don't run `/code-review` or verify: verify runs once on the merged wave (step 8), code review in the pre-merge pass.

6. As each implementer completes, merge its branch into the wave branch with a **merger subagent**, and mark that ticket done in the tracker. Once the merge is committed, the merger **cleans up** after that implementer: `git worktree remove` on its worktree, `git branch -D` on its branch, and `git push origin --delete` on the branch if it was pushed. Done when every wave ticket is merged, marked done and cleaned up.

   Mergers run only the cheap checks of what they merged (type checks, quick stages, the unit or backend tests of both sides of any conflict), never end-to-end tests and never the full suite.

7. Run the change-aware tests for the whole wave on the wave branch (everything the wave's diff against its base affects, end-to-end specs included), now that every ticket is in, to catch tickets that break each other. This is the wave's first and only end-to-end run before the user checks it: implementers and mergers ran none, so it is also the first run of every spec the wave added. Run it on the user's main machine when it's reachable (see the `lean-tests` skill). Fix what fails in a single **fixer subagent** that reads each failure's trace and log first, cleaned up the same way once merged, rerunning only the failed tests until they pass. When one ticket causes most of the failures (it is badly broken, not tangled with others), give that ticket its own fixer on its own branch, in parallel with the fixer for the rest, so it doesn't hold up the wave. Don't run the full suite here: it runs once per wave, on the wave branch in the pre-merge pass (once, on one machine, the fastest, never split between machines, with other machines covering only OS-specific stages: see the `lean-tests` skill's fast full run), started as soon as the user has checked the wave. Every failure in that run gets fixed before merging, including failures that also happen on the default branch and flaky tests: find the cause and fix it, never rerun until green, skip, or wave it through as pre-existing.

   Fixers hold their tests to the same `test-audit` gate.

8. **Verify the merged wave before the checklist.** Once step 7 is green, run the repo's verify (its own verify skill when it has one, else Claude Code's) on the wave branch, covering every screen the wave touched, before the user sees anything: each screen comes up at the standard window sizes in both themes; nothing in the UI jumps, snaps, flashes or re-renders when the user acts (switches, toggles, tabs, inputs, data arriving), every change easing or cross-fading in place; controls line up (the inputs, steppers, switches and their unit words of a list or form share one column edge, labels share theirs, row heights match); no card or column has an empty tail, and wide screens are used, not left as a narrow centred strip; no text is cut off. Fix its findings in parallel, one fixer subagent per finding (or per small group sharing one cause or the same files), each with its cheap checks and the end-to-end or layout specs that would catch its fix, no end-to-end run; then verify again only the screens the fixers touched. The checklist (published by the thread running this wave) comes after this pass. Don't run `/code-review` in this run, neither per ticket nor on the wave branch: it runs once per wave, in the pre-merge pass on the wave branch, after the user has checked the wave and every fix is in. That pass goes: the full suite starts the moment the user passes the checklist and OKs the merge, detached and watched, with failures streaming out as they happen; beside it, `/code-review` and fix what it raises, verify again on the screens changed since this step's verify (checklist and review fixes) and fix what it finds, then the `test-audit` skill's audit when that skill is available; the full run's failures are fixed as they arrive, each fix proven on the main machine (reproduce the failure there first, then 3 green runs of the fixed test); then one closing run of the failed tests plus the affected tests since the full run's commit, never a second full run; then the merge. Each phase's fixes run in parallel: one fixer subagent per finding (or per small group sharing one cause or the same files), each in its own worktree, never one agent for the whole list. Review, verify and audit fixers (and fixers of the user's checklist notes) add or extend the end-to-end specs that would catch their fix but run no end-to-end tests, per fixer or per batch: only the cheap checks (type checks, quick stages, the unit or backend tests of what they changed), then merge and report their specs. The full run covers the checklist fixes and the closing run covers the rest.

9. Mark the PR ready for review. Then sweep: `git worktree prune`, and confirm `git worktree list` shows no implementer worktree and `git branch -a --list '*<wave branch>--*'` shows no implementer branch, local or remote. Clean up any that remain. Done when both come back empty; the wave branch is the only branch this run leaves.

10. Report the wave and stop: the PR, what step 8's verify found and fixed, that its pre-merge pass is still owed before merging (the full-suite run started at once, with code review, verify of what changed since and the test audit beside it, then the closing run, unless the repo's CI runs the full suite on the PR, in which case name that run), each ticket implemented, the tickets this wave unblocked (the next wave's frontier), and the tickets waiting on the user.
